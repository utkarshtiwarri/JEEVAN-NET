## Shell and tooling quirks that will cost you time

- **Quoted arguments get mangled through `cmd /C`.** `git commit -m "several words"`
  is split into pathspecs. Write the message to a file and use
  `git commit -F .git/MSG`. Same class of problem breaks `findstr /C:"a b"` with
  multiple patterns, and silently empties `$variables` in `powershell -Command`.
  One pattern per `findstr`, no `$`, no `%%{...}` in `curl -w`.
- **`for %P in (...) do ... | findstr ... && echo` does not work.** The pipe and
  `&&` do not compose inside a cmd `for` body; it reports FAIL for everything.
  Use `&`-chained individual commands.
- **`edit_file` multi-line `old_string` fails on CRLF files.** `styles.css` is
  CRLF, so a multi-line anchor returns "not found". Anchor on a single line (or
  a single line plus text you append in `new_string`). `src/**/*.jsx` accepted
  multi-line anchors fine.
- PowerShell `$j = ...` is emptied by the shell wrapper; use `read_file` instead
  of parsing files in PowerShell.

## Project-specific facts

- `jeevan-net-phase1/scripts/split-main.mjs` and `prune-dead-css.mjs` are
  **destructive one-offs that have already been applied**. Do not re-run them
  against the reorganised tree. `verify-imports.mjs` (`npm run check`) and
  `find-dead-css.mjs` are read-only and safe to re-run.
- `npm run check` is a static import check, not a test suite. Neither side has
  tests. `npm run build` **does succeed** here (~2.5 s, 523 kB chunk, one
  size warning and nothing else); the "missing
  `@rollup/rollup-linux-x64-gnu`" failure recorded in `REDESIGN_NOTES.md` is
  obsolete on this machine.
- `src/lib/api.js` mixes the live `assessPatient` fetch with five **unused**
  Supabase CRUD helpers (`saveProfile`, `getProfile`, `saveAssessment`,
  `getAssessmentHistory`, `deleteAssessment`). Nothing imports them, and unlike
  `auth.js` they call `supabase.auth.getUser()` with no null guard, so invoking
  one with Supabase unconfigured throws a `TypeError` rather than the intended
  "please log in" message. `saveProfile` also duplicates the private helper in
  `auth.js`.
- `src/styles.css` has **two** `:root` blocks (line ~10 and line ~2229) holding
  different teal values; the later one wins, so the first is dead weight. Most
  screens also set colour in inline `style={{}}`, so treat the tokens as only
  partly authoritative.
- `scripts/find-dead-css.mjs` cannot parse a ternary `className` such as
  `className={cond ? "jh-action jh-action-primary" : "jh-action"}`, so it reports
  those classes as dead. Its 26 "never referenced" names include at least four
  false positives; the genuinely dead families are the legacy
  `coordination-grid` / `timeline-*` / `record-symptom*` / `stroke-comparison-grid`
  selectors left over from the pre-redesign dashboard.
- `.tmp-auth-entry.mjs` and `.tmp-sb-stub.mjs` are **live test inputs**, not scratch:
  `scripts/check-auth-logic.mjs` bundles the first against the second as a stand-in
  for `@supabase/supabase-js`. **Do not delete them** — the auth check stops
  working. `.tmp-auth-test.mjs` is that check's **generated output**; it is written
  and then unlinked on each run, so it reappearing simply means the check ran. Safe
  to ignore, harmless to delete. (An earlier note wrongly listed the two inputs as
  disposable; only `.tmp-pd.css`, styling a `pd-` dashboard that no longer existed,
  was genuinely dead, and it is gone.)
  `scripts/splice-auth-css.mjs` and `scripts/fix-env-name.mjs` are likewise
  already-applied destructive one-offs, alongside `split-main.mjs` and
  `prune-dead-css.mjs`.
- **Facility data is now real, and that limits what the match means.**
  `src/data/facilities-osm.json` holds 129 facilities from OpenStreetMap within 6 km
  of Connaught Place, generated by `scripts/fetch-facilities.mjs`. Distance is
  computed from published coordinates; everything else is sparse — OSM publishes an
  `emergency` tag for 3 of 129 and a sector for 28 of 129, and **never** publishes
  beds, staffing or equipment.
- **The old facility fixture invented its numbers and has been deleted.** It carried
  bed counts, ratings, ETAs and five capability scores per hospital, all made up.
  `scoring.js` now scores only published signals and reports a `coverage`
  percentage alongside every match. A high match at low coverage is a weak claim
  and the UI says so.
- **Unpublished emergency capability is scored 0.35, not omitted.** Omitting it would
  let a small clinic with no data outrank a hospital that declares emergency
  services. Conservative scoring plus a visible "not published" label is the
  honest middle.
- The origin is **fixed** at Connaught Place because the app has no geolocation. A
  real deployment needs the patient's location, and a facility dataset that is not
  two years stale.
- `data/facilities.js` still imports `Emergency` as a sentinel so the word-scanning
  import check passes; the real re-export is `facilitiesDatabase`.
- Removing the fixture means `facility.beds`, `.rating`, `.eta` and `.type` no
  longer exist. The components read `distanceKm`, `etaMinutes`, `kind`,
  `emergencyDeclared`, `coverage` and `unknown` instead — check those before adding
  a new field to a card.
- The Vite dev server must stay on port **5173** (`strictPort` in
  `vite.config.js`) because the backend CORS allowlist names only that port.
- `Backend/main.py` trains both models at **import time**; a first request is
  slow and every reload retrains.
- **The backend runs here.** Python 3.13.14 with numpy 2.5.1, scikit-learn 1.9.0,
  qiskit 2.5.2 and fastapi 0.141.1 are installed, and `import main` succeeds in
  ~35 s (it trains both models at import time). The older notes claiming the
  backend had never been executed, and that `qiskit>=1.2` needed Python 3.12, are
  both obsolete.
- `Backend/model.py` holds the dataset generator, the labelling heuristic, the
  quantum feature map and both pipelines. `Backend/main.py` only composes them for
  the API. **`Backend/evaluate.py` composes the same pieces for measurement** —
  change the model in `model.py`, never in the evaluation script.
- **The scoring rule has ONE definition: `src/data/scoring-rule.json`.** Both
  `src/lib/triage.js` (imported by Vite) and `Backend/model.py` (loaded by path)
  read it, so weights and the 9/5 cut points cannot drift. It lives under
  `src/data/` because Vite can only import JSON from inside its root, and Python
  can read it from anywhere.
- **`node scripts/check-scoring-parity.mjs` is a real cross-language test.** It
  scores 435 generated forms in both runtimes (boundaries, all 64 symptom
  subsets, random, cap cases) and fails on any score or level difference. Run it
  after touching the JSON.
- **A `with { type: "json" }` import attribute is required.** Plain Node ESM
  refuses a JSON import without it (`ERR_IMPORT_ATTRIBUTE_MISSING`), and Vite 6
  accepts the same syntax, so one spelling works in both. Do not "fix" it by
  switching to `createRequire`.
- **Both models predict three bands, not a binary.** They are trained on
  `rule_level(risk_score(row))` and the reported band is `predict_proba().argmax()`.
  The earlier binary head (HIGH vs not) could never align with a three-band rule:
  agreement capped at 78.9% even at optimal thresholds. Do not reintroduce
  probability cut points.
- **`classWeight: "balanced"` is a deliberate asymmetry.** It lifts HIGH recall
  from 64% to 84% for about three points of agreement. A false HIGH
  over-escalates; a missed HIGH sends an emergency patient home.
- `Backend/evaluate.py` regenerates `docs/evaluation.md`. That file is generated —
  re-run the script instead of hand-editing it. One run takes ~1 min because the
  circuit simulation dominates.
- **Measured result worth remembering: the quantum features are worthless.** On
  identical training rows the hybrid's macro F1 leads by +0.005 — noise. Do not
  claim any benefit from the "hybrid" half; the number is in
  `docs/evaluation.md` and reproduces on every run.
- **The two engines now agree on 82% of held-out rows** (exact band), up from 67%
  before the rules were unified. Disagreement never crosses both extremes: 0 cases
  of rule-HIGH → model-LOW and 0 of rule-LOW → model-HIGH. Quote that pair, not
  just the percentage.
- The unified rule means the **critical demo preset now scores 15, not 14**
  (age 56 crosses the aligned ≥50 threshold), and the stable preset scores 1, not
  0. Both engines report HIGH / LOW respectively on those presets.
- Testing a demo payload needs the **symptoms** dict. Sending vitals alone makes
  `symptom_count` default to 0, which drops the rule score and can make a
  deliberately critical case look mild. Mirror what `src/lib/api.js` sends.
- `scripts/verify-imports.mjs` is a **word scanner, not a real import check**. It
  looks for a fixed list of symbols (`Field`, `App`, `Emergency`, …) anywhere in a
  file, so the bare word `App` in a comment (`App.jsx`) or `Field guide` in prose
  reports a failure unrelated to imports. The codebase convention for that false
  positive is a sentinel import — `data/facilities.js` and `data/doctors.js` both
  import `Emergency` without using it. Reword the prose or follow the convention;
  do not "fix" the checker.
- Supabase is optional and must stay that way: `src/lib/supabase.js` builds the
  client from `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` and exports `null`
  (plus `supabaseConfigError`) when they are missing, because the whole app still
  has to render — its sign-in gate reads `localStorage`, not Supabase. A
  committed `.env` is not used; `.env.example` documents the two variables and is
  the only env file git tracks. `src/lib/auth.js` *does* read and write the
  optional `profiles` table (`supabase/schema.sql`), falling back to
  `user_metadata` and warning instead of failing when the table is absent; the
  session probe in `main.jsx` also touches the client once on load. Three env
  files exist on disk and are gitignored: `.env`, `.env.local`, `.env.bak`.

  `03-patients.sql` remain as the individual steps but are no longer required.
  **Nothing in this repo can apply it** — there is no `service_role` key, and
  adding one to a browser bundle would bypass RLS. **The SQL editor takes SQL, not
  a file path:** pasting `supabase/setup.sql` fails with `42601 syntax error at or
  near "supabase"`. Open the file and paste its contents.

- **Email delivery is the live blocker, and the UI no longer depends on it.**
  `mailer_autoconfirm` is `false`, so password sign-up waits on a confirmation

  10-second unblock for password auth. **The email-code (OTP) sign-in was
  deliberately removed** — see the sign-in note below.
- For reference, if email ever works: a 6-digit code is only emailed when the
  Supabase **"Magic Link" template contains `{{ .Token }}`**, and **newer
  projects grey the template editor out entirely** ("Set up custom SMTP to edit
  templates"). Neither matters now that the code flow is gone; recorded so the
  next session does not re-add it and rediscover both walls.
- **Adding a column does not make it visible to PostgREST immediately.** Right
  after `alter table ... add column`, `select=<newcol>` can still return
  `42703 column ... does not exist` from a stale schema cache. Fix with
  `notify pgrst, 'reload schema';` and re-probe. Do not conclude the SQL failed
  from that error alone — confirm against `information_schema.columns` first.
- RLS being *on* is not the same as the right policies existing. With only the
  anon key you can confirm enforcement (an anonymous insert returns 401) but you
  **cannot list policies**, so a passing probe does not prove the file's policies
  were created.
- **`isDemo` is the real-account discriminator.** `defaultUser` (what both demo
  buttons return) carries `isDemo: true`; `toAppUser()` never sets it. Code that
  must not write to the database — `PatientAssessment`, `PatientHistory` — gates
  on `user.isDemo`, never on `user.email`, because the fixture object also has an
  email. `AuthModal` branches the same way: a demo session gets its profile edited
  in memory only, a real one gets an `updateMyProfile()` upsert.
- **Sign-in has two modes on `src/pages/Login.jsx`:** password (`signIn`) and
  create account (`signUp`, which also returns a session when "Confirm email" is
  off). **There is deliberately no passwordless email-code route** — it was built,
  then removed, because this project's mail sender fails (`Error sending
  confirmation email`) and a sign-in option that cannot deliver is worse than none.
  Do not re-add `signInWithOtp`/`verifyOtp` without first proving email delivery.
  `Login` still accepts an optional `initialMode` prop; `App.jsx` does not pass it.
- `src/modals/AuthModal.jsx` is a **plain profile editor**, not a verification
  gate: it saves via `updateMyProfile()` and has no code step. It previously
  demanded an emailed OTP, which made editing your own name impossible while mail
  was broken. A profile write is already scoped to the signed-in account by RLS,
  so the code added nothing but a dependency.
- To render a non-default mode in a `renderToString` check you must pass
  `initialMode` — otherwise only the password panel is in the markup. Same
  convention as the rest of the project: esbuild + `renderToString` when browser
  tooling is unavailable (it is, in this client).
- **`toAppUser()` can yield `age: "—"` and `gender: "Not specified"`** for an
  account with no profile row. Both poison downstream code: `Number("—")` is
  `NaN`, and `"Not specified"` matches no `<option>` in a gender `<select>`.
  `PatientAssessment` therefore seeds via a regex test against `defaultForm`
  (`/^\d+$/`), never `user.age || "56"`. The same guard covers a register patient
  whose age was left blank.
- `renderToString` separates adjacent text nodes with `<!-- -->`, so an assertion
  on text spanning two JSX expressions (e.g. `AGE {age}, {gender}`) fails even
  though the markup is correct. Strip `<!--[\s\S]*?-->` before matching.
- The sign-in gate is `src/pages/Login.jsx`, rendered by `App.jsx` whenever the
  `jeevan-net.session` flag is unset and no Supabase session restores, so a fresh
  browser always lands on it. **The demo buttons need no credential** — "Use Demo
  Account" and "Continue as guest" both just hand over `defaultUser`.
  `DEMO_PASSWORD` ("jeevan123") in `Login.jsx` is a dead constant left from an
  earlier design; nothing reads it. "Continue as guest" deliberately skips the
  persisted flag, so that session ends on reload; the header log-out button
  clears it.
- When browser tooling is unavailable, component correctness was checked by
  bundling with esbuild and rendering via `renderToString` (throwaway script,
  deleted after use) rather than inferred from a passing `npm run build`.
- The Voice Companion brain is data + engine, **not** the component:
  `src/data/conditions.js` (one object per disease, 26 of them) and
  `src/lib/symptomEngine.js` (scoring, negation, red-flag escalation). Adding a
  disease is a data edit, never a new `else if`. `node scripts/test-voice-engine.mjs`
  runs 45 spoken utterances against it — that script is the closest thing this
  project has to a test suite. **It must exit 0; re-run it after any edit to
  `conditions.js`.** It was red at 41/45 when first inspected, failing only on
  Devanagari input, because `escalateOn` and `emergencyAt` had been tuned against
  Romanised speech alone. Two calibration rules follow from that fix:
  (a) every `escalateOn` danger sign needs a Devanagari twin, since the Web
  Speech API returns Devanagari for `lang="hi-IN"` — a Romanised-only list
  silently never escalates on a real microphone; (b) `emergencyAt` is calibrated
  against *stacked* scores, because a phrase and the shorter phrase inside it
  both match, so a symptom-only utterance reaches 7-8 on its own.
